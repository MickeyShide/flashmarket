# Реестр выявленных проблем

## [CRITICAL] Кнопка «Оплатить» в Checkout создает неоплаченный заказ без перехода к платежному шлюзу (Ложное завершение оплаты)

### Где
Файлы:
- `frontend/src/components/Checkout/CheckoutView.jsx`
- `frontend/src/App.jsx`

Компоненты / функции:
- `CheckoutView` (`handleSubmit`)
- `App` (`currentView === 'checkout'`)

### Сценарий воспроизведения

1. Пользователь добавляет товар в корзину и переходит в чекаут `/checkout`.
2. Заполняет имя, адрес, телефон и нажимает большую чёрную кнопку **«ОПЛАТИТЬ 5 000 ₽»**.
3. Frontend выполняет резервирование и отправляет `POST /api/v1/orders/batch`.
4. Бэкенд создает заказы в статусе `AWAITING_PAYMENT` (со сроком резервирования 15–30 минут).
5. Frontend очищает корзину (`clearCart()`), показывает всплывающее уведомление: `«Заказ успешно оформлен! ID: ...»` и перенаправляет пользователя на вкладку «Мои заказы» (`/profile/orders`).
6. Платёжная сессия **не инициируется**, редирект в платёжный шлюз не происходит.
7. Пользователь видит подтверждение «Заказ успешно оформлен», закрывает вкладку и ожидает доставку.
8. Через 15–30 минут срок резервирования истекает, бэкенд отменяет заказ (`CANCELLED`), товары возвращаются на склад.

### Текущее поведение
Кнопка с текстом «Оплатить [Сумма]» и всплывающее сообщение вводят пользователя в заблуждение, будто оплата завершена, хотя заказ остался неоплаченным в статусе ожидания платежа.

### Ожидаемое поведение
- Либо кнопка должна называться «ОФОРМИТЬ ЗАКАЗ» с явным переходом к шагу оплаты;
- Либо после успешного `orders/batch` чекаут обязан автоматически вызвать `POST /api/v1/payments/orders/{firstOrderId}/checkout` и немедленно перенаправить пользователя на платёжную форму ЮKassa (`confirmation_url`).

### Почему это проблема
Потеря 100% конверсии в оплату для пользователей, оформляющих заказ через чекаут, массовое сгорание заказов по таймауту резерва, негатив покупателей.

### Причина в коде
В `CheckoutView.jsx` (строки 172–177, 347):
```javascript
// Success! Clear cart
clearCart();
const firstOrderId = createdOrdersResponse.orders?.[0]?.id || createdOrdersResponse[0]?.id || '';
triggerToast(`Заказ успешно оформлен!${firstOrderId ? ' ID: ' + firstOrderId : ''}`);
onCheckoutSuccess();
```
При этом `onCheckoutSuccess()` в `App.jsx` просто переключает экран:
```javascript
onCheckoutSuccess={() => {
  setCurrentView('auth');
  setProfileTab('orders');
}}
```

### Что необходимо изменить
Изменить флоу чекаута: после создания пакета заказов автоматически инициировать платёжную сессию для созданного заказа/чекаута через сервис payments и выполнять редирект на `confirmation_url`, либо выводить модальное окно оплаты с таймером и кнопкой перехода в шлюз.

## [CRITICAL] Эвристика `formatPrice` делит на 100 реальные рублёвые цены от 100 000 ₽ (Товар за 150 000 ₽ отображается как 1 500 ₽)

### Где
Файлы:
- `frontend/src/utils/formatters.js`

Компоненты / функции:
- `formatPrice(value, currency, isKopecks)`

### Сценарий воспроизведения

1. Администратор создает товар стоимостью 120 000 ₽ (например, эксклюзивная куртка из лимитированного дропа).
2. Покупатель открывает каталог или карточку товара.
3. Frontend вызывает `formatPrice(120000, 'RUB', false)`.
4. Функция видит `Number.isInteger(120000) && 120000 > 100000` и делит число на 100.
5. На ценнике отображается **1 200 ₽** вместо 120 000 ₽.
6. В корзине сумма также рассчитывается как 1 200 ₽.

### Текущее поведение
Любое целое число больше 100 000 при `isKopecks = false` ошибочно распознаётся как копейки и уменьшается в 100 раз.

### Ожидаемое поведение
Деление на 100 должно происходить строго тогда, когда флаг `isKopecks === true` (или когда данные явно получены из источника в копейках). Никаких неявных эвристик по величине числа быть не должно.

### Почему это проблема
Колоссальные финансовые риски: покупатели видят заниженную в 100 раз цену, требуют продажу по публичной оферте, корзина и чекаут показывают противоречивые суммы.

### Причина в коде
В `frontend/src/utils/formatters.js` (строки 18–20):
```javascript
export function formatPrice(value, currency = 'RUB', isKopecks = false) {
  let num = Number(value);
  if (isNaN(num)) return '0 ₽';
  if (isKopecks || (Number.isInteger(num) && num > 100000)) {
    num = num / 100;
  }
...
```

### Что необходимо изменить
Удалить эвристику `(Number.isInteger(num) && num > 100000)`. Конвертацию из копеек производить исключительно на основе явного флага `isKopecks` или типизированных моделей данных.

## [CRITICAL] Stale Prefetch Cache показывает уже оплаченный заказ как неоплаченный, провоцируя повторную оплату (Double Payment)

### Где
Файлы:
- `frontend/src/services/prefetch.js`
- `frontend/src/services/api.js`
- `frontend/src/components/Profile/OrdersTab.jsx`
- `frontend/src/components/Order/OrderDetailView.jsx`

Компоненты / функции:
- `prefetchOrder`, `getPrefetchEntry`, `apiJson`, `OrderDetailView`

### Сценарий воспроизведения

1. Пользователь открывает список заказов `/profile/orders`.
2. Наводит курсор на заказ со статусом `AWAITING_PAYMENT` (срабатывает `prefetchOrder`, заказ кешируется в памяти на 30 секунд).
3. Пользователь кликает на заказ, нажимает «ОПЛАТИТЬ» и переходит в ЮKassa.
4. Успешно оплачивает заказ.
5. Нажимает кнопку «Назад» в браузере или возвращается в магазин по ссылке и снова кликает на заказ в списке в течение 30 секунд.
6. `apiJson('/api/v1/orders/' + orderId)` возвращает закешированный старый ответ со статусом `AWAITING_PAYMENT`.
7. `OrderDetailView` отображает статус «Ожидает оплаты» и активную кнопку «ОПЛАТИТЬ».
8. Пользователь решает, что оплата не прошла, нажимает «ОПЛАТИТЬ» повторно и совершает второе списание.

### Текущее поведение
Кэш предзагрузки (`prefetchCache`) отдаёт устаревшее состояние заказа, игнорируя факт совершения платежа на стороне платёжного шлюза.

### Ожидаемое поведение
Данные, влияющие на финансовые транзакции и статусы заказов, не должны отдаваться из неинвалидированного in-memory кэша при открытии экрана деталей заказа (`skipCache: true` для критичных экранов).

### Почему это проблема
Двойное списание денежных средств с карты клиента, претензии, чарджбэки и ручные возвраты.

### Причина в коде
В `frontend/src/services/api.js` (строки 82–87):
```javascript
if (isGet && !options.skipCache) {
  const cachedPromise = getPrefetchEntry(path);
  if (cachedPromise) {
    return await cachedPromise;
  }
}
```
В `OrderDetailView.jsx` запрос заказа выполняется без флага `{ skipCache: true }`.

### Что необходимо изменить
Добавить `{ skipCache: true }` при получении заказа в `OrderDetailView.jsx`, а также инвалидировать кэш предзагрузки для заказов при переходе на оплату и возврате с платёжного шлюза.

## [CRITICAL] Зомби-резервы на складе и сбой заказа при последовательном резервировании нескольких позиций в корзине

### Где
Файлы:
- `frontend/src/components/Checkout/CheckoutView.jsx`

Компоненты / функции:
- `CheckoutView` (`handleSubmit`)

### Сценарий воспроизведения

1. Пользователь оформляет заказ с 4 позициями в корзине.
2. Frontend запускает последовательный цикл резервирования:
   - Товар 1: `POST /stocks/1/reserve` (успех)
   - Товар 2: `POST /stocks/2/reserve` (успех)
   - Товар 3: `POST /stocks/3/reserve` (ошибка: товар закончился или произошёл сетевой сбой)
3. Frontend попадает в блок `catch` и пытается выполнить rollback, вызывая `POST /stocks/:id/release`.
4. Если в этот момент у пользователя пропала связь, закрылась вкладка браузера или упал сервис инвентаря:
   - Товары 1 и 2 остаются заблокированными в статусе RESERVED на складе.
5. Реальные покупатели видят, что товаров нет в наличии (Out of Stock), хотя заказ не был создан.

### Текущее поведение
Клиентский код orchestrates распределённую транзакцию (Distributed Saga) через цепочку отдельных HTTP-запросов из браузера.

### Ожидаемое поведение
Резервирование и создание заказа корзины должно происходить атомарно на стороне бэкенда единым запросом (Unit of Work / Batch Transaction). Фронтенд не должен отвечать за сагу отката резервов.

### Почему это проблема
Уязвимость перед сетевыми сбоями браузера, блокировка складских остатков ("зомби-резервы"), потеря выручки магазина.

### Причина в коде
В `CheckoutView.jsx` (строки 109–134 и 182–195):
```javascript
for (const item of cart) {
  const reserveRes = await apiJson(`/api/v1/stocks/${item.id}/reserve`, ...);
  successfulReservations.push(...);
}
...
// В catch блоке:
for (const resItem of successfulReservations) {
  await apiJson(`/api/v1/stocks/${resItem.productId}/release`, ...);
}
```

### Что необходимо изменить
Перенести атомарное резервирование всей корзины целиком на бэкенд в эндпоинт `orders/batch` или `checkout`, убрав клиентский цикл резервирования и клиентский откат.

## [CRITICAL] Отсутствие Batch Payment: невозможность оплатить корзину целиком

### Где
Файлы:
- `frontend/src/components/Checkout/CheckoutView.jsx`
- `frontend/src/components/Order/OrderDetailView.jsx`
- `frontend/src/components/Profile/OrdersTab.jsx`

Компоненты / функции:
- `CheckoutView`, `OrderDetailView`, `OrdersTab`

### Сценарий воспроизведения

1. Пользователь положил в корзину 3 разных товара (худи, кроссовки, кепку).
2. Заполнил адрес и оформил заказ.
3. Бэкенд создал 3 отдельных заказа в БД (batch lines).
4. Пользователь переходит в «Мои заказы» и видит 3 отдельных строки заказа со статусом «Ожидает оплаты».
5. Чтобы купить корзину, пользователь должен:
   - Открыть первый заказ → нажать «Оплатить» → ввести карту на ЮKassa → вернуться.
   - Открыть второй заказ → нажать «Оплатить» → ввести карту на ЮKassa → вернуться.
   - Открыть третий заказ → нажать «Оплатить» → ввести карту на ЮKassa → вернуться.
6. Пока пользователь оплачивал первый и второй заказ, на третий заказ истёк таймаут резервирования (15 минут), и он отменился.

### Текущее поведение
В приложении нет интерфейса и флоу оплаты единого чекаута (`checkout_id`). Оплата реализована строго по одному `orderId`.

### Ожидаемое поведение
Пользователь должен иметь возможность оплатить всю корзину единым платежом по общей сумме через `checkout_id` или объединённую платёжную сессию.

### Почему это проблема
Крайне негативный UX, многократный ввод платёжных данных, риск частичной оплаты заказа и потери части позиций из-за истечения таймаутов.

### Причина в коде
В `OrderDetailView.jsx` метод `handlePayOrder` принимает только один `orderId` и вызывает `/api/v1/payments/orders/${orderId}/checkout`. В `CheckoutView.jsx` возвращаемый бэкендом `checkout_id` игнорируется (берётся только `createdOrdersResponse.orders[0]?.id`).

### Что необходимо изменить
Реализовать поддержку оплаты общего чекаута через `checkout_id` / batch payment на клиенте и бэкенде.

## [CRITICAL] Утечка и перемешивание корзин разных пользователей на одном устройстве при Logout / Login

### Где
Файлы:
- `frontend/src/context/CartContext.jsx`
- `frontend/src/context/AuthContext.jsx`

Компоненты / функции:
- `CartProvider`, `AuthContext` (`logout`)

### Сценарий воспроизведения

1. Пользователь A заходит на сайт, собирает в корзину товары своего размера (например, размер S).
2. Нажимает «Выйти из аккаунта» (`logout()`).
3. Пользователь B на том же компьютере входит под своим логином.
4. Открывает корзину: в корзине лежат товары пользователя A.
5. Пользователь B нажимает «Оформить заказ» и случайно заказывает чужие товары/размеры на свой аккаунт.

### Текущее поведение
`CartContext` сохраняет корзину в неперсонализированный ключ `localStorage.getItem('fm_cart')`. При вызове `logout()` корзина не очищается и не изолируется по `user_id`.

### Ожидаемое поведение
Корзина либо должна быть привязана к ID пользователя (`fm_cart_${userId}`), либо сбрасываться/синхронизироваться с бэкендом при смене сессии.

### Почему это проблема
Нарушение приватности данных, ошибочные заказы и финансовые потери клиентов при использовании общих или семейных устройств.

### Причина в коде
В `AuthContext.jsx` метод `logout()` очищает только токены и профиль, не вызывая `clearCart()` из `CartContext`. `CartContext.jsx` использует глобальный ключ `CART_KEY = 'fm_cart'`.

### Что необходимо изменить
Изолировать хранилище корзины по `user_id` или очищать локальную корзину при смене пользователя.

## [HIGH] Тупиковое состояние на странице возврата платежа при задержке webhook (`PaymentReturnView.jsx`)

### Где
Файлы:
- `frontend/src/components/Payment/PaymentReturnView.jsx`
- `frontend/src/components/Order/OrderDetailView.jsx`

Компоненты / функции:
- `PaymentReturnView`, `OrderDetailView`

### Сценарий воспроизведения

1. Пользователь оплатил заказ в ЮKassa и вернулся на URL `/payment/return?order_id=...`.
2. Из-за сетевой задержки или очереди вебхук от ЮKassa задержался на 90 секунд.
3. `PaymentReturnView` опрашивает API 15 раз (`MAX_POLLS = 15`) с увеличивающимся интервалом и останавливается на состоянии `state = 'delayed'`.
4. На экране отображается жёлтое сообщение: *«Проверка занимает больше времени. Статус обновится в заказе.»*
5. Кнопки «Повторить проверку» (Retry) на экране **нет**.
6. Пользователь нажимает «Открыть заказ», переходит в `OrderDetailView`.
7. В `OrderDetailView` автоматического поллинга статуса платежа **нет**; если заказ загрузился со статусом `AWAITING_PAYMENT`, кнопка «ОПЛАТИТЬ» снова активна.

### Текущее поведение
После 15 попыток экран возврата навсегда прекращает проверку без возможности ручного повтора, а экран заказа не умеет отслеживать статус завершающегося платежа.

### Ожидаемое поведение
На экране `PaymentReturnView` при статусе `delayed` должна быть кнопка «Проверить статус снова», а в `OrderDetailView` должен работать периодический опрос, если по заказу была начата оплата.

### Почему это проблема
Пользователь не понимает, списались ли деньги, и видит предложение оплатить заказ повторно.

### Причина в коде
В `PaymentReturnView.jsx` (строки 61–65):
```javascript
if (attempt + 1 >= MAX_POLLS) {
  setState('delayed');
  setMessage('Проверка занимает больше времени. Статус обновится в заказе.');
  return;
}
```
Отсутствует функция ручного перезапуска `poll(0)`.

### Что необходимо изменить
Добавить кнопку ручной повторной проверки статуса и поддержать polling статуса платежа в `OrderDetailView`.

## [HIGH] Бесконечный шторм запросов к API при истечении таймера дропа (`Countdown.jsx`)

### Где
Файлы:
- `frontend/src/components/Drops/Countdown.jsx`
- `frontend/src/components/Drops/DropDetail.jsx`

Компоненты / функции:
- `Countdown` (`calculate`), `DropDetail` (`loadDrop`)

### Сценарий воспроизведения

1. Пользователь находится на странице дропа `/drops/:id`.
2. До старта или окончания дропа остаётся 2 секунды.
3. Таймер доходит до 0 (`diff <= 0`).
4. Функция `calculate` выполняет `if (onExpire) onExpire();`.
5. В `DropDetail.jsx` `onExpire={loadDrop}` инициирует запросы:
   - `GET /api/v1/drops/...`
   - `POST /api/v1/products/batch`
6. `setInterval` продолжает работать каждую секунду, так как условие `diff <= 0` остаётся истинным.
7. Каждую секунду `onExpire` вызывается снова, создавая непрерывный шторм сетевых запросов.

### Текущее поведение
Таймер `Countdown` не очищает интервал при наступлении события истечения и бесконечно спамит бэкенд вызовами `loadDrop`.

### Ожидаемое поведение
При первом наступлении `diff <= 0` таймер должен вызвать `clearInterval`, единожды уведомить `onExpire` и прекратить тикать.
