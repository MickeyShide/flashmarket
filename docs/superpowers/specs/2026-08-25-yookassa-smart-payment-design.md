# Интеграция Умного платежа ЮKassa в тестовом режиме

Дата: 2026-08-25

## Контекст

FlashMarket уже содержит отдельный FastAPI-сервис `payments`, локальную модель
платежа, transactional outbox и события платежной саги. Сейчас пользовательский
интерфейс создает mock-платеж, самостоятельно вызывает административное
подтверждение платежа, а затем напрямую подтверждает заказ. Это подходит только
для демонстрации и не должно использоваться с реальным провайдером.

Владелец проекта не зарегистрирован как самозанятый, ИП или юридическое лицо.
Поэтому первая версия интеграции работает только с тестовым магазином ЮKassa:
денежные средства не списываются, но API, переход на платежную страницу,
уведомления и возвраты проходят по тому же протоколу, что и в боевом магазине.

## Цели

- Подключить Умный платеж ЮKassa с `confirmation.type=redirect`.
- Использовать одностадийную оплату с `capture=true`.
- Сохранить существующую событийную сагу заказов и резервирования товара.
- Исключить доверие к данным о сумме, провайдере и результате платежа со стороны
  браузера.
- Обрабатывать повторные запросы и уведомления без двойных списаний и событий.
- Поддержать полный возврат через API ЮKassa при компенсации отмененного заказа.
- Оставить mock-провайдер для локальных и автоматических тестов.
- Не позволить тестовым реквизитам выглядеть как настроенная боевая интеграция.

## Не входит в первую версию

- Прием настоящих денежных средств.
- Фискализация и передача объекта `receipt`.
- Двухстадийная оплата и ручное подтверждение списания.
- Частичные возвраты, автоплатежи и сохранение платежных методов.
- Checkout.js, виджет и собственная форма ввода банковской карты.
- Несколько платежных попыток для одного отмененного заказа. После финальной
  отмены пользователь оформляет новый заказ.

## Выбранный сценарий

Используется Умный платеж: FlashMarket создает платеж на сервере и перенаправляет
пользователя на `confirmation_url`, полученный от ЮKassa. ЮKassa самостоятельно
показывает доступные тестовому магазину способы оплаты и возвращает пользователя
на страницу FlashMarket. Возврат пользователя не считается доказательством
успеха; финальный статус определяется только после серверной проверки API.

Параметры создаваемого платежа:

- `capture: true`;
- `confirmation.type: redirect`;
- `confirmation.return_url`: разрешенный публичный URL FlashMarket;
- сумма в рублях, точно преобразованная из целого числа копеек;
- `description`: краткое описание заказа без пользовательского HTML;
- `metadata.payment_id` и `metadata.order_id`: внутренние UUID;
- стабильный `Idempotence-Key`, производный от UUID локального платежа.

## Архитектура

### Порт провайдера

Сервис `payments` получает небольшой асинхронный интерфейс провайдера:

- создать внешний платеж;
- получить внешний платеж;
- создать полный возврат.

Реализации:

- `MockPaymentProvider` для тестов без сети;
- `YooKassaPaymentProvider` для тестового магазина ЮKassa.

Application service зависит от интерфейса, а не от HTTP-клиента. Интеграция с
ЮKassa использует асинхронный HTTP-клиент, HTTP Basic Auth, ограниченные таймауты
и структурированное преобразование ошибок. Секретный ключ никогда не попадает в
логи, ответы API или frontend.

### Конфигурация

Добавляются настройки окружения:

- `PAYMENTS_PAYMENT_PROVIDER=mock|yookassa`;
- `PAYMENTS_YOOKASSA_SHOP_ID`;
- `PAYMENTS_YOOKASSA_SECRET_KEY`;
- `PAYMENTS_YOOKASSA_API_URL=https://api.yookassa.ru/v3`;
- `PAYMENTS_YOOKASSA_RETURN_URL`;
- `PAYMENTS_YOOKASSA_TEST_MODE_REQUIRED=true`;
- `PAYMENTS_YOOKASSA_CONNECT_TIMEOUT_SECONDS`;
- `PAYMENTS_YOOKASSA_READ_TIMEOUT_SECONDS`.

При `PAYMENTS_PAYMENT_PROVIDER=yookassa` отсутствие обязательных значений
останавливает запуск с понятной ошибкой. В первой версии
`PAYMENTS_YOOKASSA_TEST_MODE_REQUIRED` имеет безопасное значение `true`: после
создания или чтения объекта провайдер обязан увидеть `test=true`. Объект с
`test=false` отклоняется и не подтверждает заказ.

Примеры окружения содержат только названия переменных и фиктивные значения.
Настоящие и тестовые секреты не добавляются в Git.

### Данные платежа

Локальная запись платежа остается источником состояния саги. Миграция добавляет
минимальные данные интеграции:

- внешний идентификатор платежа ЮKassa;
- URL подтверждения с достаточной длиной;
- внешний статус и причина отмены для диагностики;
- признак тестового объекта;
- идентификатор/ключ операции возврата при необходимости идемпотентного повтора.

Уникальность `order_id` сохраняется. Один заказ имеет одну платежную попытку.
Существующие статусы `PENDING`, `SUCCESS`, `FAILED`, `CANCELLED`, `REFUNDED`
сохраняются, чтобы не менять контракты саги.

## HTTP API FlashMarket

### Запуск оплаты

Добавляется авторизованный endpoint:

`POST /api/v1/payments/orders/{order_id}/checkout`

Endpoint не принимает сумму, валюту, пользователя или провайдера от клиента.
Он загружает платеж, ранее созданный обработчиком авторитетного события
`orders.PaymentRequested`, и проверяет владельца и срок оплаты.

Успешный ответ содержит только безопасные клиентские данные:

- внутренний `payment_id`;
- состояние платежа;
- `confirmation_url` для перехода.

Если событие создания платежа еще не обработано, endpoint отвечает специальной
конфликтной ошибкой `payment_not_ready`; frontend выполняет несколько коротких
повторов с ограниченным временем. Повторный запуск уже созданного внешнего
платежа возвращает тот же URL и не создает второй платеж.

### Получение платежа по заказу

Добавляется авторизованный endpoint чтения платежа по `order_id`. Он нужен странице
возврата и экрану заказа для отображения фактического состояния. Пользователь
может читать только собственный платеж, администратор — любой.

### Webhook

Добавляется публичный endpoint без JWT:

`POST /api/v1/payments/webhooks/yookassa`

Тело webhook рассматривается только как сигнал. Перед изменением локального
состояния backend запрашивает объект платежа у ЮKassa по внешнему ID и проверяет:

- `test=true`;
- внешний статус;
- сумму и валюту;
- `metadata.payment_id` и `metadata.order_id`;
- соответствие внешнего ID локальной записи.

Такой GET-запрос с серверной Basic Auth является основной проверкой подлинности.
Список официальных IP может использоваться как дополнительный сигнал и метрика,
но приложение не доверяет пользовательскому `X-Forwarded-For` без настроенной
цепочки доверенных прокси.

Webhook всегда идемпотентен. Уже примененное состояние возвращает HTTP 200 без
повторного outbox-события. Невалидное тело получает 400. Временная ошибка API или
БД получает 5xx, чтобы ЮKassa повторила доставку.

### Возвраты

Компенсационное событие `orders.PaymentRefundRequested` больше не меняет статус
локально. Для успешного платежа оно создает полный возврат в ЮKassa со стабильным
ключом идемпотентности. Если возврат завершается не сразу, локальный платеж
остается `SUCCESS`, а worker сверяет возврат через GET; webhook
`refund.succeeded` ускоряет эту сверку. Статус `REFUNDED` и событие
`PaymentRefunded` фиксируются только после подтвержденного статуса `succeeded`.
Отмененный возврат сохраняется как диагностическая ошибка и не выдается за
успешный.

Mock-провайдер сохраняет прежнее быстрое поведение в тестах. Частичные возвраты
не реализуются.

## Потоки данных

### Успешная оплата

1. Orders резервирует товар и публикует `PaymentRequested` с авторитетной суммой.
2. Payments consumer создает локальный платеж в `PENDING`.
3. Пользователь нажимает «Оплатить».
4. Payments создает внешний платеж с `capture=true` и стабильным ключом
   идемпотентности.
5. Frontend перенаправляет браузер на `confirmation_url`.
6. После действий пользователя ЮKassa присылает `payment.succeeded`.
7. Payments получает актуальный объект через API, сверяет данные, переводит
   локальный платеж в `SUCCESS` и атомарно добавляет `PaymentSucceeded` в outbox.
8. Orders consumer переводит заказ в `CONFIRMED` существующим способом.
9. Страница возврата опрашивает состояние заказа/платежа и показывает результат.

### Неуспешная или просроченная оплата

1. ЮKassa присылает `payment.canceled`.
2. Payments проверяет актуальное состояние через API.
3. Локальный платеж получает `FAILED`, причина сохраняется для диагностики, а в
   outbox один раз добавляется существующее событие `PaymentFailed`.
4. Orders отменяет заказ, а inventory освобождает резерв существующей сагой.

### Возврат после гонки с отменой заказа

Если `PaymentSucceeded` приходит после отмены заказа, Orders уже публикует
`PaymentRefundRequested`. Payments выполняет настоящий полный возврат через API,
а не только меняет локальный статус.

## Frontend

Экран заказа больше не:

- передает сумму и провайдера при создании платежа;
- вызывает административный `/confirm`;
- напрямую подтверждает заказ.

Кнопка оплаты вызывает checkout endpoint и выполняет переход через
`window.location.assign` только на URL, который вернул backend. Во время запуска
кнопка блокируется. Ошибки `payment_not_ready` повторяются ограниченно; остальные
ошибки показываются пользователю без внутренних данных провайдера.

Добавляется состояние возврата из ЮKassa: «Проверяем оплату», «Оплата прошла»,
«Оплата отменена» и «Проверка занимает больше времени». Страница не объявляет
успех только на основании факта возврата браузера и продолжает использовать
серверное состояние.

## Ошибки и надежность

- POST-запросы в ЮKassa всегда имеют стабильный `Idempotence-Key` не длиннее 64
  символов.
- Сетевой таймаут или HTTP 500 не трактуется как отказ платежа. Повтор выполняется
  с тем же ключом, затем состояние сверяется через GET.
- Ошибки 4xx валидируются и преобразуются в безопасные доменные коды без утечки
  тела с реквизитами.
- Смена статуса и запись outbox-события выполняются в одной транзакции БД.
- Webhook может приходить раньше возврата браузера, после него или несколько раз;
  все варианты дают один итог.
- Если локальный срок оплаты истек до создания внешнего платежа, checkout
  отклоняется. Если внешний платеж уже создан, окончательное решение принимается
  по подтвержденному статусу ЮKassa.
- Административные mock-endpoint `confirm` и `fail` недоступны обычному
  пользователю и не участвуют в сценарии ЮKassa.

## Наблюдаемость

Логи и метрики содержат внутренний payment ID, внешний payment ID, тип операции,
HTTP-класс ответа и длительность, но не содержат secret key, заголовок
Authorization или полный URL подтверждения.

Минимальные счетчики:

- создание платежа по результату;
- обработка webhook по событию и результату;
- расхождение суммы/metadata/test-mode;
- возвраты по результату;
- ошибки и таймауты API ЮKassa.

## Тестирование

### Unit

- точное преобразование копеек в строку рублей;
- формирование payload и ключей идемпотентности;
- отображение статусов ЮKassa в доменные статусы;
- проверка test-mode, суммы, валюты и metadata;
- редактирование ошибок без утечки секретов.

### API и application service

- checkout доступен только владельцу/администратору;
- сумма от клиента отсутствует в контракте;
- повторный checkout возвращает тот же платеж;
- конкурентные запросы создают одну внешнюю операцию;
- webhook succeeded/canceled идемпотентен;
- поддельный webhook не меняет состояние без подтверждающего GET;
- временная ошибка провайдера оставляет платеж в неопределенном `PENDING`;
- возврат вызывает провайдера и публикует событие только после успеха.

### Frontend

- кнопка оплаты вызывает только checkout endpoint;
- переход происходит на серверный confirmation URL;
- прямые confirm order/payment вызовы удалены;
- страница возврата корректно показывает pending/success/failure/timeout.

### Интеграционная проверка

После того как владелец создаст тестовый магазин и локально добавит реквизиты:

- успешная тестовая карта;
- отмена/неуспешная карта;
- повторная доставка webhook;
- возврат успешного тестового платежа;
- возврат браузера до и после webhook.

Тест с сетью является ручным и не входит в обязательный офлайн-набор CI.

## Развертывание тестового режима

1. Владелец регистрируется в тестовом режиме ЮKassa без указания данных компании
   и договора.
2. В локальный или тестовый secret store добавляются `shopId` и secret key.
3. Настраивается публичный HTTPS URL webhook и события `payment.succeeded`,
   `payment.canceled` и `refund.succeeded`.
4. Включается `PAYMENTS_PAYMENT_PROVIDER=yookassa` при обязательном
   `PAYMENTS_YOOKASSA_TEST_MODE_REQUIRED=true`.
5. Выполняются ручные сценарии тестовыми картами.

Для будущего приема реальных денег потребуется отдельное бизнес-решение:
оформление допустимого статуса продавца, договор с ЮKassa, настройка
фискализации и отдельное явное снятие защиты test-only. Эти действия не являются
частью данной реализации.
